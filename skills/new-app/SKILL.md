# New app

Generate a new repo with a working skeleton across five layers: API, web, Android, iOS and infrastructure, plus CI.
When you finish, the repo builds and its tests pass, and a user can sign in on every client once the cloud resources exist.
Every layer includes one complete feature: user registration, profile editing and account deletion. That feature is the
pattern for building new ones.

Nothing is copied from another repo. The specs in `references/` are the template. They describe each layer and include
exact code for the parts that are easy to get subtly wrong. If the user wants to change the stack, they edit those files.

Arguments given: `$ARGUMENTS`

## Placeholders used in the references

| Placeholder | Meaning | Example |
| --- | --- | --- |
| `<App>` | PascalCase app name | `TrailMix` |
| `<app>` | lowercase, no separators | `trailmix` |
| `<APP>` | uppercase, no separators | `TRAILMIX` |
| `<Company>` / `<company>` | company or owner prefix, Pascal / lower | `Acme` / `acme` |
| `<domain>` | apex domain of the web app | `trailmix.app` (API at `api.<domain>`) |
| `<region>` | main AWS region | `us-east-2` |

## 1. Gather inputs

| Input | If not given |
| --- | --- |
| App name | Required. It must be PascalCase letters and digits, because it becomes a .NET namespace, a Kotlin package and an Xcode target. Turn `trail-mix` into `TrailMix` and confirm |
| Company prefix | Always ask (see below) |
| Destination | Always ask (see below). The default is `./<app>` |
| Domain | `<app>.example.com`, with an item in SETUP.md to replace it |
| AWS region | `us-east-2` |
| Layers | All five. The user can drop any of them |
| Optional modules | Always ask (see below) |

Ask for everything missing in one AskUserQuestion call, with layers as a multi-select. For inputs that have a default,
don't ask. Use the default and mention it.

**Company prefix.** Never assume it. Ask, unless the user already gave it. It names the code and the store listings:
- .NET projects and namespaces: `<Company>.<App>.Api`
- Android package, iOS bundle ID and the apps' sign-in redirect scheme: `com.<company>.<app>`

These identifiers can't change after the apps are published, so it has to be the user's choice. In the question, suggest up to two
likely values as options, for example from the git `user.name`, the email domain, or the parent folder of the working directory.
The user can type their own with "Other". Like the app name, it must be PascalCase letters and digits. Turn `acme-labs` into
`AcmeLabs`, confirm it, and use the lowercase form (`acmelabs`) wherever the references say `<company>`.

**Destination.** Ask where the new app should go, unless the user already gave a path. The default is `./<app>`, a folder named
after the app (in lowercase) inside the current working directory. Show it as a full path in the options:
- `./<app>`, for example `C:\Projects\trailmix` (recommended)
- "Other", for a path the user types

The destination must be empty or not exist yet. If the chosen folder already has files in it, say so and ask again rather than
writing into it. If the current folder is inside a git repository (`git rev-parse` succeeds), warn in the question that the new
app would be nested inside that repo. Keep `./<app>` as the default, and let the user pick another path.

**Modules.** Every app includes the two required modules, **Email (SES)** and **Images (S3)**, without asking.
The optional modules are **AI (Bedrock)**, **Maps & geocoding**, **Worker & queue (SQS)**, **Payments (Stripe)** and **Report & block**.
Always ask about them, even when the other inputs were given. A question can offer at most 4 options, so use two multi-select
questions in the same AskUserQuestion call, each module with a short description: one for **AI, Maps & geocoding, Worker & queue**
and one for **Payments, Report & block**. Don't merge modules into one option to make them fit.
The answer form can't be submitted until every question has a selection, so make the modules optional: add a last option
**None** ("Skip these modules") to each of the two questions. That keeps the first question at 4 options and the second at 3.
Say in each question's text that the modules are optional.
Build only the ones the user picks. If the user picks None, skips the question or says none, build none from that question.
If they pick None together with a module, build the module. Never add an optional module because it seems useful.
If users will see each other's content, mark Report & block as recommended in the question, because the App Store and
Play Store require it.

## 2. Generate, one layer at a time

Read each layer's reference just before you build that layer. You don't need them all at once.

| Order | Layer | Reference |
| --- | --- | --- |
| 1 | API | `references/api.md` |
| 2 | Web | `references/web.md` |
| 3 | Android | `references/android.md` |
| 4 | iOS | `references/ios.md` |
| 5 | Infrastructure + CI | `references/infrastructure.md` |
| with each layer | Required modules, plus the optional ones the user picked | `references/modules.md` (each module touches several layers, so add its parts while you build each layer) |

The API comes first because building it writes `openapi/api.json`, and both the web client generator and the mobile models use that file.

How to use the references:
- **Code blocks are exact.** Copy them, substitute the placeholders, and change nothing else. They hold fixes for real
  failures, and the comments in them say what each one prevents. Keep those comments.
- **Prose and tables are requirements.** Write that code in the conventions described.
- **Versions are known-good pins.** Use them. If one doesn't resolve, use the newest patch of the same major version and
  mention it in the report.

**Gate between layers:** run the layer's build and tests before starting the next layer, and fix failures first. A broken API
contract or auth setup spreads into every layer built after it. If a layer can't be built on this machine (iOS needs macOS,
and Android needs an Android SDK), check it by reading instead: every file referenced in `project.yml`, the manifest and
navigation must exist. Record it as not built.

## 3. Repo-level files

Write these after the layers are done:
- `README.md`: one-line product description, a table of folders, an architecture sketch of the chosen modules, local
  development steps for each layer, test commands, and the CI pipelines.
- `CLAUDE.md`: the conventions future sessions need. Include the endpoint → service → repository pattern, where dependency
  injection is registered, "run `yarn orval` after API changes and never edit `generated/`", `VITE_*` config, XcodeGen as the
  source of truth for the iOS project, the user/profile feature as the pattern to copy, and the build and test command
  for each layer.
- `SETUP.md`: fill in `references/setup-checklist.md` with the real names. Include only the layers and modules that were chosen.
- `.gitignore` at the root and for each layer, as each reference says.

Run `git init -b main` but don't commit. The user reviews the scaffold first.

## 4. Report

Tell the user:
- where the repo is, and which name, domain, layers and optional modules were used
- one line per layer: passed, failed (with the error) or not built (with the reason)
- any version that differed from the pins, and anything you were unsure about
- that SETUP.md lists the steps that need accounts or consoles, and which ones come first
